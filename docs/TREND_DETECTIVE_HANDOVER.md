### Evidence from the branch review

- **Seasonal fit.** `Task4/stats.py` and `Website/stats.js` estimate the calendar-month levels and the straight-line slope together. This avoids absorbing part of the trend into the monthly levels when a record starts or ends midyear or has gaps. The review ran all **37 Python tests**. After regenerating the Python reference, JavaScript passed **2,051 checks on 105 series**.
- **What the tests establish.** The new regression tests independently check the slope against a fit with calendar-month indicators. The Python/JavaScript parity tests check agreement between implementations. The branch still uses the full time sum of squares and `n_eff − 2` for slope uncertainty, even though the joint slope is identified by variation within each calendar month. Ask P4 to check the standard error, degrees of freedom, and interval coverage against the joint model before adopting the inference change. Check the chart band separately from the interval for the slope.
- **Stored map and live results can disagree.** `Website/data/world.json` is byte-for-byte identical before and after `b6d1e27`. Once the method is settled, rebuild the 5° overview and regenerate the browser data so the map, point analysis, and demo verdicts use the same method. Check points near the 0.05 and 0.10 verdict thresholds.
- **Search results need a common test.** The reviewed branch reports 36/36 correct measurements, 32/36 correct place-plus-measurement matches, and 1/12 unavailable requests answered without a note on 48 held-out draft questions. The Searchlight branch reports 25/28 correct measurements and 1/14 suggestions for unsupported requests on a separate set with locations supplied. These runs used different questions and starting conditions. Test both on the same unseen full queries before changing the default. Include lowercase place names, place aliases, multiple requested measurements, and requests for NO₂, streamflow, hourly data, and forecasts. Record whether the answer matched the requested measurement or offered a clearly labelled related one. ## NASA Space Apps discussions worth using

1. **Search by concept, then check data coverage.** The accepted answer in #2152 suggests mapping user language to a controlled vocabulary, then checking location, date range, and resolution. With the current POWER catalog, check availability against the returned series and its actual date range. Consider NASA CMR, GCMD keywords, or CF names when the site spans multiple archives. Keep ranking and wording separate from the calculations, which stay in code. [Accepted answer in #2152](https://github.com/nasa/spaceapps/discussions/2152#discussioncomment-19614459)
2. **Keep the fast overview and fetch each selected point on demand.** The same answer recommends this combination. Explain that ByteMe's 5° squares display sampled points, and that the clicked location retrieves its own gridded series. Nearby results can give context, but shared weather and data processing make adjacent cells correlated. A 3×3 window on the 5° overview spans far more than the local neighborhoods discussed in the thread. Elevation and land cover also matter. If a scan highlights significant findings across many variables or locations, review multiple-testing control separately from temporal autocorrelation or spatial dependence. [Accepted answer in #2152](https://github.com/nasa/spaceapps/discussions/2152#discussioncomment-19614459) · [Jim Acker’s reply](https://github.com/nasa/spaceapps/discussions/2152#discussioncomment-19617791)
3. **Keep data expansion optional.** The thread suggests IMERG for precipitation, MODIS for vegetation or land-surface temperature, GLDAS or SMAP for soil moisture, and OMI or TROPOMI for trace gases. Jim Acker adds AIRS for atmospheric temperature and water vapour. If a use case needs one of these, first confirm the product, dates, units, masking, and access path. A Hydrology Time Series request in #2074 failed to retrieve the subset output. Treat such failures as retrieval errors until coverage is independently confirmed. [Dataset suggestions](https://github.com/nasa/spaceapps/discussions/2152#discussioncomment-19614459) · [AIRS reply](https://github.com/nasa/spaceapps/discussions/2152#discussioncomment-19617791) · [Hydrology troubleshooting](https://github.com/nasa/spaceapps/discussions/2074#discussioncomment-19605961)
4. **Show a real investigation in the demo.** #1843 points back to the challenge brief for the deliverable. The brief asks users to choose a variable and a region, see the time series, and learn the direction, size, and significance of change. #2194 advises putting actual charts and findings into the pitch once verified. A two-place case can show how geography changes the result. Use matched time windows and describe the strength of each site's evidence. [Navigator reply in #1843](https://github.com/nasa/spaceapps/discussions/1843#discussioncomment-19558324) · [Challenge brief](https://www.spaceappschallenge.org/2026/challenges/earth-system-trend-detective/) · [Pitch advice in #2194](https://github.com/nasa/spaceapps/discussions/2194#discussioncomment-19618216)
